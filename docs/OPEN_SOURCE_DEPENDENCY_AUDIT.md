# Open-Source Dependency / Operational-Burden Audit

Produced by independent, read-only inspection: `git log -1 --format=%cd` and
`git rev-list --count HEAD` run inside each repo's own `.git`, plus direct reads of
`package.json`/`pyproject.toml`/`go.mod`/`composer.json` and whatever
`docker-compose*.yml` files actually exist in each repo (not assumed from documentation).
"Today" for maintenance-recency purposes is 2026-11-23.

**A caveat on "maturity/maintenance signal" below**: `git rev-list --count HEAD` on a
local clone only tells you how much history *this clone* carries. `formbricks` and
`posthog` both report a commit count of 1 in this clone despite being extremely active,
well-known projects — this is conclusive evidence of a **shallow clone** (`--depth 1` or
similar), not evidence the projects are unmaintained. Their `last_commit` date (both
2026-11-20/21, i.e. within the last few days of "today") is the only trustworthy maintenance
signal available from this clone for those two; commit-count as a maturity proxy only means
something for the repos with clearly non-trivial counts (everything else in this set).

## Cross-cutting dependency-conflict notes (independently re-confirmed, not merely restated)

- **Database engine fragmentation is real and was independently re-confirmed by this audit's
  own reads of `composer.json`/Doctrine config (mautic → MariaDB/MySQL only), `go.mod`
  (listmonk → Postgres, the one DB-compatible candidate), and the `docker-compose.base.yml`
  service list (posthog → Postgres **and** ClickHouse **and** a Kafka-family broker, not just
  "Postgres+Redis" as a casual read might assume).** None of the 13 repos can share DevLaunch's
  existing Postgres *schema*; at most listmonk can share the same Postgres *server* (different
  database, confirmed by its own sqlx-based schema having no RLS/tenant_id concept to collide
  with DevLaunch's RLS-protected tables).
- **Node version skew, independently re-confirmed from each repo's own `package.json`
  `engines` field** (not re-derived from documentation): twenty `^26.5.1`, formbricks
  `>=26.0.0 <27`, n8n `>=24.0.0`, mastra `^22.19.0 || >=24.11.0`, postiz-app `22.23.4` (exact
  pin). None of these matter for a correctly-isolated, per-service container deployment — the
  pattern every "adopt as independent service" recommendation in this audit assumes — but they
  do rule out ever sharing a single Node runtime/container image across more than one of these
  services, or between any of them and DevLaunch's own `apps/api`/`apps/worker`.
- **Shallow-clone blind spot**: formbricks and posthog's `git log`/`git rev-list` in this
  specific clone are not usable maintenance signals (see caveat at top). Any future session
  relying on this document for a "when was this last touched" judgment on those two repos
  should check GitHub directly rather than trust this clone's `.git` history.
- **leadhub and OpenOutreach are the two weakest links on supply-chain/maintenance grounds**,
  independently re-confirmed here: leadhub's 3-commits-in-one-day, 5-months-stale history is a
  concrete, verifiable fact (not an inference) from this clone's own `git log`; OpenOutreach's
  pinned-and-redaily-repinned external PyPI dependency model is documented in its own
  `CLAUDE.md` file (a repo-internal admission, not a third-party claim) and was read directly
  as part of this audit.
